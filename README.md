# 轻聊助手（LiteChat）v1.25

**自动找到你的聊天窗口，自动读聊天记录，自动生成 3 条回复，一键填进输入框。**
手机和电脑都有，配置只需要**一个第三方大模型 API**。

> 发送永远由你自己按。程序只把候选回复复制到剪贴板（两端都能一键填进聊天输入框），
> 从不自动点发送，不碰转账红包，不读别的程序的数据。

基于 [Jev 聊天助手](https://github.com/jev-chat/jev-chat-jarvis)（MIT）二次开发的简化版，
详见 [NOTICE](NOTICE)。

**源码仓库**：<https://github.com/xiaoluo139/litechat>

### 支持范围（先说清楚边界）

**手机端**

| 聊天软件 | 微信 4.x、微信 3.x、QQ / TIM、飞书、钉钉有专门布局；**其它任何软件**都能一键从窗口列表里选，选一次就记住 |

## 二、v1.16 ~ v1.20：手机端识别与悬浮窗

你说手机端开倒车：微信认不出来、不自动生成、其它软件也识别不准、还特别慢。
这次在模拟器上把它跑起来抓日志，**三个真原因全抓到了**，其中一个确实是最近才引进的。

### 根因 1（本次倒车的直接原因）：截图偏移算错，整块识别区域被平移

手机端取画面有两条路：整屏截图，和"只截前台窗口"（Android 14 才有，原本是当作省流的
优化，放在了**第一条**）。问题在于窗口的坐标是**拍之前**读的，而截图是**之后**才拿到的：
一次切窗口的滑入动画被拍到一半，程序认为"这个窗口从 x=666 开始"，于是它拿到的
1080 宽的整屏画面被当成了"从第 666 像素开始的窗口画面"。

结果是：消息区在屏幕上被整体平移着裁——**一段四句话的对话，只读回来三行，而且全被判成
"我说的"**。既然"最新一条对方消息"永远不变，程序就**再也不会生成回复**。
日志里原样长这样（修复前后）：

```
修前： shot=1080x2400 scale=1.0,1.1183597 origin=666,0
      read=me:昨天那份材料你看|me:客户那边催得有点|me:行，那我 发你
修后： shot=1080x2400 scale=1.0,1.0 origin=0,0
      read=other:昨天那份材料你看过了吗? | other:客户那边催得有点急,今天
           | me:我早上看了一半，下午给你 | me:行，那我三点再来问你，我
```

两处都修了：

* **整屏截图回到第一顺位**，它的坐标不需要猜（原点就是 0,0）；"截窗口"只在整屏被系统
  拒绝时才用，而且只有在窗口矩形**确实落在屏幕内、而且确实更小**时才敢用；
* 新增一层**几何自检**：`scale=1.118` 也是错的——整屏截图被拿"可用区域"（2146px）
  去除 2400px 的画面高度，等于把所有纵坐标拉伸 12%。现在整屏截图强制 1:1，
  窗口截图必须先通过"矩形可信"检查。这条规则是纯函数，配 7 个单测
  （`CaptureGeometryTest`），其中就包含"x=666 那次"的真实数据。

### 根因 2：浮窗被拍进了截图，我们自己的字被当成对方说的话

读屏时会把浮窗拍进去。原来的对策是"截图前把浮窗藏起来"——**这条路在 Android 15 上根本
不成立**：我先试 `INVISIBLE`，再试整窗 alpha=0，最后试把窗口从 WindowManager 里摘掉，
实测**窗口摘掉 293ms 之后，截图里浮窗还在**（系统把最后一帧又给了你）。于是
"技能 调用军师 取消军师""对话人 自动跟随""推荐2·30%"这些**我们自己的字**被当成消息
发给了模型——这正是"牛头不对马嘴"的一大来源。

现在改成不藏了：**浮窗老老实实待着，落在浮窗范围内的 OCR 行直接丢掉**。
遮挡区按"浮窗在屏幕上的真实位置"算（不是布局参数，实测两者差了约 150px），
并且把**最近 2 秒内出现过的所有浮窗形状取并集**（浮窗会随内容变高变矮，而截图可能是
几百毫秒前的）。顺带把"每秒闪一下"也去掉了——那正是你之前说的"老是一闪一闪"。

### 根因 3：微信主界面被当成聊天会话

微信的消息文字对无障碍是隐藏的，所以只能靠截图认。但"认"这件事原来只看**有没有气泡
节点**——没有就当会话处理。结果在微信**聊天列表**上，程序会把中间那一列联系人名字
当成消息读出来，给模型一个"联系人名单"去回复。

现在补了一条判断：**标题栏读到"微信 / 通讯录 / 发现 / 我 / 朋友圈"就是不分析**，
面板直接提示"这一屏是微信主界面，打开一个聊天再读"。只做**完全匹配**（"微信团队"
"朋友圈代购"这种真会话名不受影响），有 3 个单测钉住。

### 顺带提速

标题栏和消息区原来要**两次** OCR。它们上下紧贴，现在合成**一次**读，
省掉一次完整往返（手机上约 0.3 秒），每次回复都受益。

### v1.17：在 **Android 16（API 36）** 上实测后又补的两处

你的手机是安卓 16 以上，所以我把这版又搬到 Android 16 模拟器（1080×2400、
420dpi、API 36）上从头跑了一遍，果然又抓到两个问题：

**① 面板展开时会挡住聊天内容，把对方的消息一起读丢了。**

浮窗进截图这件事，上一版用的是"把落在浮窗范围内的 OCR 行丢掉"。Android 16 上面板
更高（1344px），日志里出现了 `read 21 line(s), 19 under the panel`——21 行里 19 行
被当成浮窗文字丢掉，**其中就有对方的气泡**，于是新消息读不到。

根治办法是不再"截全屏再抠掉浮窗"，改成**只截聊天窗口本身**（Android 14 起有的
`takeScreenshotOfWindow`）。浮窗是另一个窗口，天然不在画面里——面板开多大都不影响。
它唯一的弱点是坐标依赖"窗口在屏幕上的位置"，所以现在会**在截图前后各读一次窗口边界**，
两次不一致（窗口正在滑动/动画中）就作废并退回整屏截图；整屏那条路仍然保留遮罩兜底。
日志里两条路各自长这样：

```
shot=1080x2400 scale=1.0,1.0 origin=0,0 windowScoped=true   ← 只截聊天窗口，面板不在画面里
read=other:昨天那份材料你看过了吗? | other:客户那边催得有点急,今天
     | me:我早上看了一半,下午给你 | me:行,那我三点再来问你,我     ← 四条全读到，左右都对
answered in 2758 ms skill=general noThinking=true
```

**② 新消息实测**（安卓 16 上点测试聊天框发一条新消息）：

```
read=other:昨天那份材料你看过了吗? | other:客户那边催得有点急,今天
     | me:我早上看了一半,下午给你 | me:行,那我三点再来问你,我
     | other:材料我明天上午给你          ← 新来的那条
decide(v3) screenRead=true autoAnalyze=true latest=other auto=true
answered in 2758 ms skill=general noThinking=true
```

### v1.18：换人还答上一个人 / 点「对话人」悬浮窗就消失 / 慢

你反馈的三件事都在安卓 16 模拟器上复现并修掉了，根因都挺具体：

**① 换联系人之后，回复还是上一个人的** —— 姓名比对太松。

程序靠标题栏的名字判断"换人了没有"。原来的规则是"两个名字相似度 ≥ 50% 就算同一个人"，
而两个字的中文名只要有一个字相同就有 50%：`老刘/老李`、`老王/老张`、`张三/张四`
全被判成同一个人。于是**切换根本没被发现**，上一次的候选留在面板上，程序继续按上一个人
的对话答。现在：

* 两个字的名字必须**完全一致**才算同一个人（三个字以上才允许一个字 OCR 误差，
  而且姓氏必须一致）——宁可多读一次，也不能答错人；新增 4 个单测；
* 一旦发现换人，面板**立刻**换成「已切到「X」· 正在读这段对话，读完就出候选」，
  不再让上一个人的候选停在屏幕上（`android-37-v1.18-switch-immediate.png`）；
* 如果你锁定的是别人，也会把上一个人的候选清掉，并写清楚怎么改回自动跟随
  （`android-38-v1.18-pinned-elsewhere.png`）。

**② 点「对话人」，悬浮窗就消失** —— 三个原因叠在一起。

* **名单被后台刷新冲掉**：程序每秒都在读屏，每次读完都会重画面板；名单刚打开约 1 秒
  就被下一次刷新覆盖，看起来就是"闪一下没了"。现在名单打开期间是**模态**的：后台拿到
  的新结果先存着，等你点「返回」再画出来（`android-39-v1.18-picker-holds.png` 是打开
  8 秒后仍然在的名单）。
* **自己的窗口被当成"你离开了聊天"**：在部分 ROM 上，一碰浮窗，系统报的"当前窗口"
  就是我们自己。旧代码把这当成"用户切走了"，直接 `hide()` 掉整个浮窗。现在遇到自己
  的包名什么都不做。
* **在触摸处理里重建/移除面板**：点选项会同步重建面板、点"隐藏助手"会同步移除窗口，
  都是在触摸派发过程中动的，改成下一帧执行；名单构建也加了保护，出错只在面板上提示，
  不会把服务带崩。
* 顺带揪出一个更严重的：`toggle()` 先把"已展开"标记翻过去、再检查窗口在不在。第一次
  失败（比如悬浮窗权限刚授予、窗口还没建起来）就把标记卡在"已展开"，
  **之后面板再也打不开**。现在先确保窗口存在，再翻标记。

**③ 生成慢** —— 截图有 1 秒节流，被节流丢掉的请求原来要干等下一个屏幕事件
（最多再等 1 秒）。现在到点**自动重试**，这段死时间没了。

实测（安卓 16 + 真实 LongCat-2.0）：换人后面板 1 秒内显示"已切到「X」"；名单打开 8 秒
不动、选人后浮窗稳定、返回后候选正常出来；安卓单测 **111 个全绿**。

### v1.19：换人"跟不上"的真正兜底 + 对话人按钮放两个地方

**① 换人跟不上 —— 读屏原来完全靠"聊天软件通知我们"**

程序以前只在聊天软件发无障碍事件时才去看屏幕。微信把消息区对无障碍隐藏，
某些版本**切联系人的时候根本不给事件**，于是程序一直没重读，面板就一直停在上一个人的
对话上——你切了人它却不知道。现在改成：**有事件立刻读，没有事件也每 2 秒自己读一次**。
日志证据（全程没有任何操作、聊天界面也没变化）：

```

06:26:39.758 ocr[testchat] taking a screenshot
06:26:41.763 ocr[testchat] taking a screenshot
06:26:43.771 ocr[testchat] taking a screenshot     ← 固定 2 秒一次，不依赖聊天软件配合
```

实测换人：点一下标题栏换到另一个人，**3 秒内**面板就变成
「已切到「老刘」/ 正在读这段对话，读完就出候选」，上一个人的候选同时清空
（`android-43-v1.19-switch-3s.png`）。

**② 「对话人」按钮放两个地方，一定看得到、一定点得到**

* 浮窗面板里原来是「对话人」三个小字 + 一个 24dp 高的灰色小胶囊，太小也容易忽略。

* 更重要的：**App 主界面新增了「对话人 / 正在回答谁」选择区**
  （`android-41-v1.19-home-picker.png`）。那是普通应用窗口，触摸永远有效——
  就算你手机上浮窗被系统限制点不到，也能在这里选人、切回自动跟随。

**③ 前两版那批修复继续保留**：两个字的名字必须完全一致才算同一人（换人才不会被当成
没换）、名单打开期间不被后台刷新冲掉、自己浮窗的点击不再被当成"离开聊天"、
`toggle()` 的状态不会卡死。

### v1.20：微信读不到 —— 只影响微信的那条路

你反馈"微信读不到屏幕内容，其它软件都正常"。这个组合本身就是线索：别的软件有文字节点，
只有微信的正文对无障碍是**隐藏**的，它**只能靠截屏识别**。而截屏这条路被一个开关整体挡住：

```
设置 → 读不到文字时用截屏识别（默认开）
```

这个开关一旦关掉（或以前被关过），**微信就彻底读不到**，而其它软件完全不受影响——
和你的现象一模一样。现在改成按"这条链路本身是不是只能截屏"来判断：

* 微信（消息正文被隐藏）、以及通用识别（本来就没有文字节点）→ **必须**截屏，不受开关影响，
  由各自的「读取微信」「自动识别其它聊天软件」开关管理；
* 真正有文字节点的软件（QQ/飞书/X）遇到读不到文字时 → 才走这个"回退"开关。

实测（安卓 16，**故意把那个开关关掉**）：微信版式链路照常读到全部消息并出候选——
`android-45-v1.20-wechat-ocr-off.png`，日志 `read=other:… | me:…` 共 7 条，
`answered in 4135 ms`。

同一版还收紧了两处**只可能误伤微信**的地方：

* 微信的**截屏改为固定用整屏画面**（不再用"只截当前窗口"）。微信的聊天页是它自己画的，
  只截窗口有可能拍不到那部分内容或拍到空白——这正是"只有微信读不到"的另一种可能。
* "微信主界面不分析"的判断**只保留「微信」这一个标题**（原来还包含 通讯录/发现/我/朋友圈），
  每多一个词就多一次把真会话挡掉的机会；宁可偶尔把联系人列表当会话，也不能让微信读不了。
* 新增**空白画面识别**：截到纯色（内容被系统/应用挡住）时，面板直接说
  "截到的是空白画面（内容被系统或该应用挡住了截图）"，而不是含糊的"没认出文字"；
  微信连续两屏读不到字也会给一句可操作的提示。

本轮回归：Windows 77 + 安卓 112 单测全绿；8 套设备脚本全 PASS（延迟中位 0.55 秒）；
v1.20 正式签名包在安卓 16 上安装启动正常（`versionCode 21 / versionName 1.20`）。

### v1.23：电脑端"识别窗口"读到了不相干的内容

你发来的截图里，面板「对方最近说」写的是 `1 子！好久不.."`、`0 湖南省 月神中秋 | 祝大..`、
`□ 小鲸智 ℃ T` —— 那些**全是左边会话列表里的联系人名字和消息预览**，不是右边聊天窗口里的
内容。所以模型才会"牛头不对马嘴"：它看到的根本不是这次对话。

根因有两个，都在电脑端：

**① 消息区裁剪的左边界是写死的 222px（微信 4.x）。**
微信的会话列表宽度是**可以拖的**。列表比这个常量宽时，裁剪就从列表中间开始 ——
整列联系人被当成"对话"读进提示词。修复：**从截图像素里自动找"列表/聊天区"的分界线**
（列表是一整块纯色面板，聊天区是壁纸，找到那块面板的最后一列就得到了边界）。
实测：列表 380px 的窗口，检测出 387（写死的常量是 280）；列表 280px 的窗口检测出 287；
其它无关窗口（NVIDIA 覆盖层、ChatGPT 等）都老老实实回落到常量，没有误判。

对照实验（同一台机器，同一个假聊天窗口，列表拖到 380px）：

```
修复前（关掉检测）： 【要回的那句】，别老蘸菩手机 行，那我三点再来问你   ← 妈妈那条预览"别老熬夜看手机"混进来了
                    对方：这边 # 老是：斤不 客户那边催得有点急，今天个说法吗
修复后：            【要回的那句】行，那我三点再来问你
                    对方：昨天那份材料你看过了吗？
                    对方：客户那边催得有点急，今天个说法吗
                    我：我早上看了一半，下牛给你答复
```

**② 微信 4.x 的输入框比记录的更高，那一小条被读成了"最新消息"。**
在你这台机器的真实微信窗口上实测：输入框的顶边在客户区底部往上 131px 处，而布局里写的是
87px —— 于是输入框的一小条进了画面，里面那个光标/草稿被 OCR 成 `0`，
面板就把「要回的那句」显示成 `0`（模型的回复当然是牛头不对马嘴）。
现在把微信 4.x 的下边界改成实测的 130px。

**③ 顺带修掉"带空格的时间戳"**：OCR 经常把 `15:46` 读成 `1 5 ： 4 6`，
而过滤规则要求数字紧挨着，于是时间戳活下来变成"最新消息"。现在允许数字之间有空格
（两端同步，手机端也改了），真实消息（`今天下午三点见`、`9月29日开会`）不受影响。

验证：Windows 单测 **83 个全绿**（新增 5 个"找分界线"的用例）；8 套电脑端设备脚本全 PASS
（延迟中位 0.51 秒）；安卓单测 **113 个全绿**；修复后在**你这台机器的真实微信窗口**上复测，
面板读到的是真实会话内容，`0` 和列表预览都不再出现。

（标题栏那一行保持原来的固定裁剪：把边界检测也用到标题上时，会话名会贴到图片边缘，
Windows 的识别器会把整行丢掉 —— 实测在某个像素上就会发生。标题本来读得对，就不动它了。）

### v1.25：手机端悬浮窗「总是不见 / 点不开」

这次是三个独立的原因叠在一起，每一个都会让浮窗消失或者按不动：

**① 窗口被系统收走了，程序自己不知道。** 程序一直用"我加过一个窗口"当作"窗口还在
屏幕上"。MIUI / HyperOS 这类 ROM 会随时把 `TYPE_APPLICATION_OVERLAY` 窗口摘掉
（省电策略、没允许「后台弹出界面」、权限被系统改回去）。窗口没了，标志还是"在显示"，
于是所有"没有浮窗才补一个"的检查全被跳过 —— 这一整段服务生命周期里浮窗再也不会出现，
看起来就是"按钮总是不见"，而且因为它其实不在屏幕上，点当然也点不开。

修法：窗口自己报告"我被摘掉了"（`onDetachedFromWindow`），摘掉后 **0.4 秒重挂**；
再加一条 **2 秒自检**（`ensureVisible`）兜住"没有回调的静默移除"；如果刚挂上就又被摘走，
连续 3 次就退避到 30 秒一次，并提示去打开「后台弹出界面」——而不是每秒跟系统硬抢。

**② 「隐藏助手（本次）」是单向门。** 它把窗口删掉，而当时没有任何东西会再把它加回来：
点过一次就只能重装。现在它叫 **「隐藏助手 10 分钟」**，到点自己回来；主界面也多了一个
**「悬浮窗不见了？→ 重新显示」** 按钮（计数器写进配置，运行中的服务收到就立刻重挂）。

**③ 白名单没命中就把整个浮窗藏起来。** 名单是决定"回答谁"的，不该决定"按钮在不在"。
现在只跳过分析，浮窗留着。

顺带修掉两个会让人觉得"识别不到"的真 bug（都是这轮在模拟器上测出来的，跟上面的现象独立）：

- 判断"这一屏是不是纯黑/被防截屏"用的是 **4×4 网格取样**，正好从两个气泡中间的空隙穿过去
  —— 一屏完全能读的聊天被判成"纯黑、窗口受保护"，直接放弃识别。现在 **15×15**。
- 浮窗面板**收起之后**，它上一次的位置仍然被当成"自己的 UI"从识别结果里剔掉
  （实测一屏 21 行里 17 行被丢）。现在只在面板真的展开时才算遮挡区 —— 收起后是 1 行。

## 三、v1.15：修「没分清谁说的 / 识别不出来 / 回复牛头不对马嘴」

反馈截图里，面板写着「最近消息（没分清谁说的）」，内容只有两行时间戳
（`昨天 22:18`、`昨天 22:35`）——**真正的那句话根本没被读出来**，
所以既"识别不出来"，也"生成不了回复"。查下来是四个独立的 bug，两端都有份。

### 根因 1：带时钟的日期分隔行，没被当成装饰行过滤掉

`昨天 22:18` 不是消息，是聊天软件自己画的日期分隔。原来的过滤规则只认
**单独的**「昨天」或**单独的**「22:18」，`昨天 22:18` 两头都占一点，正好漏网。
它被当成一条消息，又坐在最下面，于是"最新消息"变成了一个时间戳——
模型拿到时间戳，当然写不出切题的回复。

改成：日期 / 星期 / 日期时间后面都允许再跟一个时钟
（`昨天 22:18`、`星期一 22:18`、`9月29日 22:18` 全部过滤掉）。
**真实消息不受影响**：`今天下午三点见`、`9月29日开会`、`昨天那事我想想`、
`我在长沙` 这些都有单测钉住，不会被误杀。两端同一套规则
（`windows/winchat.py` 的 `_NOISE_LINE` 与 `android/.../core/MessageKeys.kt` 的
`NOISE_LINE`）。

### 根因 2：屏幕上只有一条气泡时，程序告诉模型「分不清谁说的」

屏幕只剩一条靠左的气泡时，原来会走"两边方向不可靠"的分支，提示词里
**没有【要回的那句】**，模型只能自己猜——这是"牛头不对马嘴"最直接的来源。

现在分三档：气泡颜色读到了就一定算数；位置（靠左 / 靠右）也算数，
但只在有把握的时候才算数；居中又没有颜色的，仍然老实说"分不清"，
不会硬编一个方向骗模型。

### 根因 3：自动跟随会把浏览器 / 编辑器当成聊天窗口

"跟随窗口"原来会跟**任意**前台窗口：你一切到浏览器或编辑器，
程序就把那一屏的字当聊天记录发给了模型。这也是一部分"牛头不对马嘴 + 乱码"。

现在只跟随两类窗口：**被认出来的聊天客户端**（微信 / QQ / TIM / 飞书 / 钉钉），
或者**和你锁定过的那个窗口同一类**的窗口。你在列表里手选一次的那个窗口，
以后照旧跟着走。

### 根因 4（手机端）：一条设置读不出来，整个分析就崩掉

安卓的 `SharedPreferences` 是强类型的。某个键要是以别的类型存着
（旧版本写的、或者手工改过配置文件），读的那一刻直接抛
`java.lang.String cannot be cast to java.lang.Boolean`，
面板只显示一行"出错了"，而其它设置其实全都正常。

现在读取一律容错：坏掉一条设置只损失那一条，不会让整个功能不可用；
万一还是抛，也换成看得懂的中文提示，而不是把 java 的报错串丢给你看。
配套的 `tools/set_android_prefs.ps1` 也改成按类型写（布尔就写 `<boolean>`），
不再自己造出这种坏数据。

### 实测证据（用 LongCat-2.0 真接口跑的，不是 mock）

## 五、v1.12：对方连发多条消息不再卡死

反馈：「一旦对方发送两条或多条信息的时候就分不清了，然后长时间都卡在那里无法触发自动生成回复」。

### 真正的机制：把过期答案丢掉时，忘了松开"正在分析"的锁

实测复现出来了（`tools/verify_inflight_messages.py`，把模拟接口调成 6 秒才回）：

```
--- message 1 ---
requests while it is thinking: 1 (should still be 1)
--- message 2 arrives mid-request ---
anchor of the follow-up     : (none)      ← 第二条永远不再被问
--- and it still answers the next one ---
anchor of the third         : (none)      ← 之后全都不动
```

原因：第 1 条消息的请求还在路上，第 2 条来了。程序会把"上一条的答案"判定为过期并丢掉——**但丢掉时没有把 `正在请求` 这个开关关掉**。于是之后每次想生成都被"上一次还在跑"挡住，一直等到看门狗（电脑端 50 秒）才松开；手机端更糟，**没有看门狗，会一直卡到下次换会话为止**。这就是"分不清 + 长时间卡住"。

同一类问题还有一处：**手机端把"窗口句柄变了"当成换了会话**。微信弹出表情面板、贴纸选择器时窗口句柄会变，于是正在途中的答案被判为过期丢掉——然后又踩上面那个"锁没松开"的坑。

### 修法

1. 丢掉过期答案时**一定松开请求锁**，并且**立刻把排队中的那条消息接着分析**
   （电脑端 + 手机端都改了）。
2. 手机端的"还是同一个会话吗"改成**只看 App + 会话名**：窗口句柄变化（表情面板、贴纸、
   系统弹窗）不再算换人；但"来了新消息"仍然会让在途答案作废——因为它的锚点是旧消息。
3. 顺带把模拟接口的 `MOCK_DELAY_MS` 解析改健壮（空字符串不再把接口整挂）。

修复后的实测（同一套慢接口测试）：

```
--- message 2 arrives mid-request ---
anchor of the follow-up     : 【要回的那句】客户那边已经等了两天了     ← 补问的就是第二条
--- and it still answers the next one ---
anchor of the third         : 【要回的那句】那就今天下班前吧
--- switching conversation mid-request ---
anchor after the switch    : 【要回的那句】行，我这就发你             ← 在途切会话也能恢复

message arriving mid-request handled: PASS
```

手机端（模拟器，接口故意设成 6 秒，连点两下输入栏发两条消息）：

```
I LITECHAT: answered in 6313 ms skill=general noThinking=true
I LITECHAT: ocr[...] read=… | other:材料我明天上午给你 | other:那下车的会改到四点了,你
I LITECHAT: answered in 6019 ms
I LITECHAT: answered in 6026 ms      ← 三次请求依次推进，末次锚点就是最新那条
```

另有 `tools/verify_double_message.py` 覆盖"两条一起到""两条短消息隔 0.8 秒到"两种时序。

## 六、v1.11：换人之后不再回答上一个人（+ 你可以自己选对话人）

反馈：「多窗口对话时，切到另一个人，生成的还是上一个窗口的内容，新窗口根本没识别」。

### 三个原因，每个都会单独造成这个现象

| # | 原因 | 表现 |
|---|---|---|
| 1 | 电脑端**绑定窗口后就不再重新识别**。PrintWindow 会把那个窗口画得干干净净，哪怕它已经被别的窗口盖住 | 你切到另一个聊天窗口，程序还在读旧的那个，回复自然还是上一个人的 |
| 2 | 在途的请求**没有作废机制**。切到新人之后，上一个人的回答才回来，直接画到新对话的界面上 | 界面显示的是新会话，内容是旧会话 |
| 3 | 手机端微信的**会话名只能靠截图认**（无障碍树是空的），而当时的代码把"没读到名字"和"同一个人"当成一回事 | 换联系人后既不清空旧候选，也不重新分析，看起来完全没反应 |

### 修法

1. **跟着你走**：每秒看一次前台窗口，只要它是下拉列表里能选到的聊天窗口，就切过去读
   （`verify_conversation_switch.py` 第一步：把第二个窗口拿到前台 → 下一次请求的
   【要回的那句】变成新会话的那句）。
2. **换人就作废**：每个请求带一个序号，切窗口/换联系人时序号 +1，回来的旧答案直接丢掉
   （日志：`[conversation] dropping a stale answer`）。
3. **标题变了就是换了人**：同一个窗口里换了联系人，标题（微信就是那行名字）一变，
   就清空旧候选、重置去重状态、立刻重新分析。
   手机端日志：`conversation changed in the same window (3 chars -> 2 chars)`。

### 新增：自己选对话人

面板上多了一行 **对话人**（电脑端在「当前会话」下面，手机端在「技能」下面）：

- **自动跟随**（默认）：跟着你切换的窗口/联系人走。
- **锁定某人**：点开列表选一个人，之后**只分析 TA 的消息**；切到别人时面板会直接说
  「当前是「张三」，你锁定的是「李四」，所以不分析」。
- 列表里的名字是**程序读到过的会话名**（手机端微信靠 OCR，偶尔会把名字读错，
  比如"李沅汐"读成"本沅火"——列表显示的是它读到的那个，所以选它仍然有效）。
- 读不到名字时（窗口太小/字体太小），锁定会**放行并在面板上说明**，
  而不是静默地什么都不做。

**一个明确的边界**：程序**不会去点你的聊天软件**替你打开某个聊天——那等于操作你的微信。
所以这个列表是用来"锁定/监控谁"的，切换聊天还是你自己在微信里点，程序跟着走。

## 七、v1.10：让模型别想太久，军师从 15-25 秒降到 3-5 秒

反馈：「自动生成的回复太慢了，特别是调用军师」。

### 慢在哪：慢在模型"想"，不在程序

把每一段都量了一遍（同一句话、同一个模型 LongCat-2.0）：

| 测的是什么 | 结果 |
|---|---|
| 程序侧：消息出现 → 请求发出 | **0.5 秒**（本来就不慢） |
| 参考文档从 1500 字砍到 400 字 | 15.1 秒 vs 14.0 秒 —— **几乎没差** |
| 参考文档全去掉（提示词只有 133 字） | **25.0 秒** —— 反而更慢，全是噪声 |
| 让模型"别写思考过程" | 19-21 秒 —— 没用，它照样在想 |
| **输出上限压到 600 / 900 token** | 思考直接把预算吃光、**没有答案**（600 token 全用在"想"上） |
| 看服务端返回的用量 | `reasoning_tokens` 125 个 → 约 10 秒；905 个 → 约 15 秒 |

结论：**推理模型把思考当正文生成，思考多长就等多久**，而且同一句话 14-25 秒都可能。
提示词、参考文档长度都改不动它。

### 解法：直接让模型别思考

实测 LongCat 认这两个开关（任选其一都行）：

```
{"thinking": {"type": "disabled"}}
{"chat_template_kwargs": {"enable_thinking": false}}
```

同一句话、同一个模型、同一个军师提示词，**只加这一个参数**：

| | 关之前 | 关之后 |
|---|---|---|
| 军师（实测 4 次） | 14.0 / 16.0 / 23.8 / 25.0 秒 | **3.4 / 3.6 / 4.0 / 4.4 秒** |
| 通用 | 4.4 / 7.9 / 15.1 秒 | **2.3 / 3.8 秒** |
| 思考 token | 900-1300 | **0** |

程序从不显示思考过程，所以那些 token 纯粹是在让你等。

**双端实测（走程序自己的代码路径、真实接口、真实对话）：**

| 平台 | 军师模式 |
|---|---|
| Windows（这条对话的真实微信窗口） | 3.5 / 5.2 秒（原来 14-25 秒） |
| 安卓（模拟器 + 微信版式测试 App，`adb logcat` 里的 `answered in`） | **2907 / 3082 / 3231 / 6586 ms** |

### 默认开，但不会把不支持的接口搞坏

这个参数不是所有接口都认。程序的做法是：

1. **默认发送**这两个开关（设置里有「关闭模型思考（更快，推荐）」，可以关）；
2. 接口若返回 **400 / 415 / 422**（"不认识这个字段"），**立刻去掉参数重发一次**，
   答案照样拿到，并**记住这个域名**，之后不再试；
3. 这种情况下面板/状态栏会说一句「这个接口不认识"关闭思考"的参数，回复会慢一些」，
   而不是让你莫名其妙地等。

这条安全网有专门的回归测试 `tools/verify_thinking_fallback.py`：它起一个
**严格校验请求体**的本地假接口（见到未知字段就 400），验证三件事——第一次能靠回退拿到答案、
第二次不再白发一次、关掉设置后完全不发。

顺带修的两处：模型偶尔会返回 **6 条**候选（关掉思考后实测出现），现在**只取前 3 条**；
安卓端新增一行 `answered in 3082 ms` 的日志（只有耗时、没有聊天内容），
以后说"慢"可以直接看这个数字。

## 八、v1.9：四条反馈的根因都在「预算」和「坐标」上

这一版没有加新功能，修的是**上一版真跑起来才暴露的问题**。

### 1. 「自动生成的回复牛头不对马嘴、还经常出乱码」——根因是推理模型

用你的 LongCat-2.0 实测抓到了真凶：**它是推理模型**，回答前先输出一大段思考。
程序原来给输出留了 **320 token** 预算，这 320 个 token 全被思考吃掉，
`finish_reason` 是 `length`，**`content` 字段根本不存在**——只回来了 `reasoning_content`。
旧代码把这段"思考过程"当成回复，于是候选里出现的是模型的自言自语。

```
（修之前，LongCat-2.0，320 token）
choices[0].message = { "role": "assistant",
                       "reasoning_content": "\n1. **分析输入：**\n * **会话：** 轻聊测试会话…",
                       "content": ← 不存在 }

（修之后，给推理模型留出预算，同一句话同一个模型）
intent : 催结果给客户交代
advice : 三点前给结论带上方向
reply 1: 能，我手上那份刚弄完，马上接着看，三点前肯定给你个说法
reply 2: 三点准时来找你，就算定不下来也给个方向先安抚客户
reply 3: 三点见，我抓紧弄
```

三处改动：

1. **预算**：默认从 320 → **1600**（这是个"上限"，不是"目标"，普通模型照样写完就停）；
2. **一次性重试**：如果第一次回来的东西里一条回复都没有（推理模型没写完、
   或回答了但格式乱），就**追加一句"不要输出思考过程"、把预算放大到 3200 再问一次**；
3. **解析器**：改成扫描**成对的 `{...}` 并从最后一个开始试**。
   旧代码取"第一个 `{` 到最后一个 `}`"，模型在正文里写一个花括号就能把整段答案毁掉，
   然后退化成"拿前三行当回复"——那三行往往就是它的思考笔记。

`reasoning_content` 有内容而 `content` 不存在时，程序**不再把思考当答案**，
而是明确报「模型只输出了思考过程」——比给你三条废话强。

### 2. 「手机端微信自动回复又不能用了」——裁剪区把最新那条切掉了

上一版为了修"最新消息读不到"，改用窗口节点的底边算裁剪区；但**内嵌窗口（没铺满屏幕）**
的情况下这会**把导航栏减两次**，裁剪区底部比正确位置高了整整一个导航栏，
最新那条消息又掉到裁剪区外——于是"能看见对话、永远看不见要回的那句"。

现在两条路都算，**取更靠上的那个**：

```
内容底边 = min(窗口自己的底边, 屏幕高 − 导航栏)
裁剪区底边 = 内容底边 − 输入栏(54dp)
```

铺满屏幕（edge-to-edge）和内嵌两种机型都对；导航栏高度还被限制在屏幕的 12% 以内，
因为某些 ROM 会把横屏的导航栏值（145dp）当成竖屏返回。

### 3. OCR 放大是**帮倒忙**——实测后撤掉

上一版给手机端加了 2 倍放大。做 A/B（同一屏、同一台模拟器、连拍多帧）后：

| | 读到的内容 |
|---|---|
| **1 倍** | `昨天那份材料你看过了吗?` / `客户那边催得有点急` / `我早上看了一半` |
| 2 倍 | `昨无那份材料你看过了吗?` / `容户那边催得有点急` / `我旱上看了一半`，还有一帧把对方的气泡判成了"我" |

放大后的重采样把字的边缘糊掉了，ML Kit 反而更容易认错。**默认改回 1 倍**，
代码里留了这次实测的记录。顺带把自动回复的读超时从 25 秒放宽到 40 秒
（推理模型就是慢），并且**超时不再自动重试**——等一次已经够久了。

### 4. 「调用军师和取消军师没啥区别」——现在有可见隔离

以前两个模式只是换了系统提示词，界面上看起来一样。现在军师会**多返回一个字段**
（对局势的判断），面板把它和**实际用到的那两篇参考文档**一起显示：

```
军师模式 · 判断：他在借客户施压，要的是明确时间 · 参考：获得领导青睐：从价值匹配到信任建立的实用指南
```

通用模式没有这一行，也不会向模型要 `stance`。同一句话两个模式的真实输出对比：

| | 通用 | 军师 |
|---|---|---|
| 判断 | — | 老板催进度，需要明确今天交付时间 |
| 建议 | 三点前给结论带上方向 | 明确时间节点，有阶段性成果就先给 |
| 回复 1 | 三点见，我抓紧弄 | 能给的，我抓紧两点前看完，三点前先给您个初步结论。 |

### 5. 顺带：LongCat 进了服务商预设

`LongCat 龙猫（美团）` 现在在两端的下拉里，地址 `https://api.longcat.chat/openai/v1`、
模型 `LongCat-2.0`，选完只要粘 key。

切换技能时，手机端浮窗**不再闪一下**（v1.8 修的，见下）。

## 十、v1.8 顺带修掉的三个真 bug

1. **手机端点技能按钮时浮窗闪一下。** 切换技能会弹一个提示（"已调用狗头军师…"），
   而这个提示窗口属于本应用自己的包名，无障碍服务把它当成了"用户打开了轻聊助手"，
   于是把浮窗撤掉、又在下一次事件里建回来。现在自己的提示窗口在 2 秒内被识别并忽略。
   验证：点按钮后连拍 8 帧，**8/8 帧浮窗都在**（v1.8 之前是 1/8）。
2. **手机端"最新那条消息读不到"。** 服务的 `displayMetrics` 给的是**可用区高度**
   （模拟器 1080×2400 的机器上报 2146），而截图是**整屏**。两者混用让消息区底部少算了一个
   状态栏的高度，**最新那条消息正好落在裁剪区外面**——程序看得见对话，却永远看不见要回的那句。
   现在改用窗口节点的真实底边。验证：日志里裁剪区从 `(0,254-1080,1879)` 变成
   `(0,254-1080,2133)`，新收到的两条消息都被读出来（`other:材料我明天上午给你`）。
3. **手机端 OCR 不放大。** 聊天字号小，ML Kit 直接认字错得比放大了还多；
   电脑端早就在用 3 倍放大，手机端一直是原图。现在放大 2 倍（带像素上限，
   低端机不会因为一张大图爆内存）。

另外把"对方正在输入…"的**乱码版本**也当噪声过滤了：OCR 经常把这句话读成
`三在窪入一` 这种样子，短语匹配抓不到，于是每次闪烁都被当成一条新消息。
现在**很短、又同时含"在/入/输/正"里两个不同字**的行直接丢掉（限 6 字以内，
`现在在路上了` 这种真回复不受影响）。

## 十一、v1.4 修的是「回复牛头不对马嘴」

### 根因一：屏幕只显示一条消息时，程序骗了模型

这是最主要的原因。屏幕识别如果只看到一条消息，程序没法判断是谁说的，
但旧版本会对模型说「这一屏没能区分我和对方，**全部按对方说的处理**」——
于是**你自己刚发出去的那句话被当成对方说的，模型就在回复你自己**。

现在：

- 电脑端**读气泡颜色**判断谁说的。微信给自己发的消息画绿底，对方的是白底，
  颜色比左右位置可靠得多 —— 尤其是只有一条消息、没有参照物的时候。
  （只认"明显偏绿"，其他颜色一律交回给位置判断，避免深色主题或别的软件误判。）
- 真的分不清时，**不再编造"对方说"**，而是把整段对话交给模型并明说：
  「请先判断最后一条是谁发的：如果是对方发的就回复它；如果是我自己刚发的，
  就回复它前面那句。」界面上那一栏也从"对方最近说"改成"最近消息（没分清谁说的）"。

### 根因二：没有告诉模型"要回的是哪一句"

旧提示词只说"这是聊天记录，给三条回复"。模型得自己猜要回哪句，猜错就是答非所问。
现在输入被拆成明确的结构：

```
【会话】李沅汐
【关系】对方是我的老板
【要回的那句】客户那边催得有点急，今天能给个说法吗
【上文，越靠下越新】
对方：昨天那份材料你看过了吗？
我：我早上看了一半，下午给你答复
```

提示词也跟着重写，硬性要求：三条都必须**直接回应【要回的那句】**、不许复述对方的话、
长度和语气要贴着对方那句、三条策略各不相同、聊天记录是屏幕识别的可能有错字要按最合理的意思理解、
不要编造记录里没有的时间金额。

### 顺带改进

- 送给模型的上下文从 12 条增加到 20 条（输入 token 便宜，答偏了才贵）。
- 电脑端消息区 OCR 倍率从 2 调到 3（实测 2/3/4 三者中 3 最干净，4 会掉字）。
- 新增 `tools/verify_prompt_anchor.py`：直接抓取程序**实际发给模型的内容**来验证 ——
  这是唯一能证明"回复锚在对的那句上"的办法。

### 验证结果

```
--- what the app asked the model ---
【会话】未命名会话
【关系】对方是我的老板
【要回的那句】i: 材料我明天上牛给你     ← 对方最新那句（"上牛"是 OCR 错字）
【上文，越靠下越新】
对方：阝份材料你看过了吗？
对方：；那边催得有点急，今天骨个说氵去吗
我：我早上看了一半，下午给你答复        ← 我自己的话被正确标成"我"
对方：那我三点再来问你
------------------------------------
prompt anchored on the right message: PASS
```

## 十二、v1.6：悬浮窗不再一闪一闪 + 换壁纸也能分析

反馈：「悬浮窗老是一闪一闪的，而且还无法分析出自动回复内容」。两个问题，两个原因。

### 一闪一闪：检测不到目标时把浮窗藏了起来

`isCurrent()` 里有一段：发现"当前活动窗口"不是那个会话时，就把悬浮窗**整个隐藏**。
而"当前活动窗口"会**频繁地短暂变成别的窗口**——微信的表情面板、贴纸选择器、
"+"菜单、系统弹窗，每一个都是独立窗口。于是浮窗被藏起来，下一个事件又把它显示回来，
一隐一现就是你看到的闪。

现在这个检查**纯粹只做判断，没有任何副作用**：真的切到别的 App 会由窗口切换事件单独处理。
同时"窗口句柄变了"不再被当成"换会话了"——只有 **App 或会话标题** 变了才算换会话，
所以表情面板弹出时面板内容也不会被清空重建。

### 分析不出来：我加的"这像不像聊天界面"判断被壁纸骗了

上一版为了不误答通讯录列表，加了一条判断：**聊天界面背景是灰色**。
而**你的微信换了聊天壁纸**（截图里能看到卡通背景），背景不是灰的 → 被判定成"不是聊天界面"
→ 直接跳过分析，面板就停在「分析当前对话」。

这条判断整个删掉了。判断错方向的代价完全不对称：误判成"不是聊天"会让程序**什么都不做**，
而误判成"是聊天"最多是多问一次模型、面板上显示一行明显不对的内容 —— 你一眼就能看出来。

另外日志还暴露一个连带问题：换壁纸后颜色采样偶尔失灵，最后一条消息被判成"我"，
而旧逻辑要求"最后一条必须是对方"才分析，于是**又一次静默丢弃**。
现在只看"最新的对方消息有没有变过"——你自己发消息不会改变它，只有对方回话才会。

### 在设备上验证过（壁纸场景）

我把测试聊天界面的背景从微信默认灰换成了**壁纸色**（`android/testchat/`），
完整复现你的情况，结果（截图 `docs/verification/android-19-wallpaper-chat-works.png`）：

```
decide(v3) screenRead=true autoAnalyze=true latest=other auto=true    ← 分析
decide(v3) screenRead=true autoAnalyze=true latest=me    auto=true    ← 不再误杀
skipped: no new incoming message                                      ← 没有新消息时正确跳过
[mock] POST /v1/chat/completions
```

面板正常显示出「对方意图 / 紧张度 / 建议 / 3 条候选回复」，
四条气泡全部识别正确，绿气泡认成"我"。

## 十三、v1.5：手机版微信真正修好了

上一版加了微信适配，但**在你手机上完全没反应**。原因不是配置问题，是三个实打实的 bug，
我在模拟器上用「长得像微信的聊天界面」逐个复现并修掉了。

### bug 1：微信把整棵树藏起来时，程序直接判定"不在聊天窗口"

微信 8.0.52 之后对无障碍服务返回**空根节点**。旧代码在树里找不到气泡节点
（`com.tencent.mm:id/bkl`）就返回 null，而"返回 null"的含义是**不在聊天窗口**——
于是连截屏兜底都不会触发，微信就是一片死寂。

现在：找不到气泡节点时，返回"这个界面要用截屏读"，并给出消息区的位置，让截屏链路接手。

### bug 2：微信没有气泡几何信息，导致截屏只发生一次

截屏前有一道"指纹"闸门（防止同一个画面反复截屏），它的指纹是由**气泡矩形**算出来的。
微信不给气泡矩形，于是指纹是个常量——**第一次之后永远不会再截屏**。
现在这类"没有几何信息"的界面走另一条路：靠截屏自身的 ≥1 秒限频 + 下游的"是不是新消息"判断来刹车。

### bug 3：判断"这是截屏读的"用了一个会被覆盖的成员变量

截屏和 OCR 是异步的，回调要几百毫秒后才回来；这期间下一个无障碍事件已经把那个
成员变量重置了。结果就是**读到了内容、却不触发分析**（日志里能看到 `msgs=4` 却没有后续）。
现在这个判断跟着快照本身走，不会被覆盖。

### 现在的三条路

1. 树的文字可见 → 直接用（最快、最准）；
2. 树里有气泡但没文字 → 逐个气泡矩形截屏 OCR（和飞书同一套，谁说的按左右位置）；
3. 整棵树是空的（微信现状）→ **截消息区整块 OCR，用气泡颜色判断谁说的**
   （微信自己发的消息是绿底，对方是白底）。

第 3 条完全不依赖微信的节点树，是这一版能让微信跑起来的关键。

### 在设备上验证过

微信本身装不进模拟器，所以我写了一个**只画微信版式的测试 App**
（`android/testchat/`，只在 debug 包里注册，永不进正式包）：
灰底、白色对方气泡、绿色自己的气泡、同样的标题栏和输入栏高度。

结果是整条链路跑通（截图见 `docs/verification/android-17-screenshot-chat-reading.png`）：

```
I LITECHAT: ocr[com.litechat.testchat] taking a screenshot (region=true rects=0)
I LITECHAT: ocr[com.litechat.testchat] msgs=4 manual=false
[mock] POST /v1/chat/completions        ← 真的调用了模型
```

面板上出现了「微信隐藏了消息文字，这里用截屏识别」、紧张度 3/9、
对方意图、建议，以及 3 条带「复制 / 填入」的候选回复。
四条气泡全部识别正确，绿气泡也被正确认成"我"。

### v1.4 的初版做法（已被上面取代，留作记录）

v1.4 第一次尝试读微信，当时是这样的（v1.5 又补了上面那三个 bug）：

1. **走微信的气泡节点**（`com.tencent.mm:id/bkl`）：拿得到文字就直接用；
2. 拿不到文字时，**对每个气泡矩形单独截屏 OCR**（和飞书同一套办法）——
   谁说的由气泡的水平位置判断，比整屏 OCR 准得多；
3. 设置里新增 **「读取微信」** 开关（默认开）。关掉就完全不碰微信，只提示一句。

**必须说清楚的代价**：读微信要用截屏识别，而截屏正是微信风控关注的行为；
另外微信可能会给聊天界面加防截屏保护，那种情况下会失败并在面板上说明原因。
不想承担这个风险，把「读取微信」关掉即可，其它软件不受影响。

## 十四、v1.3 修的是「候选回复一直跳、选不中」

反馈的原话是「明明已经自动生成了回复内容，但他来回给我跳让我选不了」。
根因有两个，两端都修了：

**1. 聊天窗口画的"装饰"被当成了新消息。** 微信在最后一条消息下面会画一行时间戳，
   对方打字时还会闪出「对方正在输入…」——这两行**会自己出现、消失、变化**。
   程序把它们当成"对方又说话了"，于是每闪一次就重新问一次模型，
   面板也就每闪一次回到「正在想…」。现在这些行在进入分析前就被过滤掉了
   （时间戳、日期、星期、「××撤回了一条消息」「以下为新消息」「拍了拍」
   「消息已发出，但被对方拒收」等系统提示都算）。

**2. 重新生成时会先把候选卡片清空。** 就算真的需要刷新，旧做法是
   "清空候选 → 显示正在想 → 等结果"。用户手已经伸过去了，卡片正好消失，
   所以"选不了"。现在**已经显示出来的候选永远留在原地**，
   进度只显示在标题右边（`更新中… 1.7 秒`），等新结果回来再整块替换；
   如果新结果和旧的一样，连重绘都不做（重绘本身会吃掉已经按下去的那一次点击）。
   手机端同样：面板里已有候选时，刷新只动标题上的一个小字，不动卡片。

### 回归测试（`tools/verify_no_flicker_restart.py`）

它让假聊天窗口**连续 24 秒闪烁**时间戳 + 「对方正在输入…」，然后发一条真消息：

```
requests after startup           : 1
blinking 时间戳 + 对方正在输入… for 24s ...
requests after 24s of flickering : 1  (delta 0)
requests after a real message    : 2  (delta 1)

flicker ignored + real message still answered: PASS
```

闪烁期间 **0 次多余请求**，真消息仍然只发 1 次。
`docs/verification/windows-05-keeps-suggestions-while-loading.png` 是刷新进行中的截图：
头部显示「更新中… 1.7 秒」，而三条候选卡片和按钮**原地没动**。

## 十五、v1.2 修的是「慢」

上一版有人反馈「自动生成的回复内容这么慢」。实测下来**不是模型的锅**：
用真实 DeepSeek 官方 key 打一次，**0.85 秒**就返回了。慢在程序自己身上，一共四处：

**1. 屏幕没变也在反复识别。** 以前每 2 秒无脑截一次图、跑一次 OCR，
   还额外再截一次会话标题条识别一次。现在先比对像素指纹，**一模一样就直接跳过 OCR**；
   标题条只在真的变了才识别。空闲时每轮只花约 18 毫秒（原来约 173 毫秒）。

**2. 任何一点文字变化都要重新问模型。** OCR 每一帧读出来的字会有细微差别，
   于是同一个消息被判成"新的"，一次又一次地问模型 —— 表现出来就是永远停在「正在想…」。
   现在只有**最新一条对方消息真的变了**才问：OCR 抖动、时间戳、你自己发的消息都不算。
   再叠一条「1.2 秒内不重复问」的闸门兜底。

**3. 轮询太慢、而且卡住不返回就永远卡住。** 以前 2 秒才看一次屏幕，请求还允许卡 60 秒，
   卡住时面板一直显示「正在想…」，后续消息也一起被挡住。现在：
   轮询 0.6 秒一次（有第 1 条兜底，快了也不费性能）、请求 25 秒超时、
   超过 30 秒强制放弃并给出原因，期间面板**实时显示已用秒数**。

**4. 请求本身就带着一笔额外开销。** 每次请求都重新做一遍 TLS 握手；
   提示词很长；一次要生成 1024 token。现在连接复用（启动时还会预热），
   提示词压缩到三分之一，**3 条回复改成先写、每条限制 26 字**，输出预算降到 320 token。

### 实测数字

| 指标 | 上一版 | 现在 |
|---|---|---|
| 消息出现 → 发出请求 | 2 秒以上 | **0.52 秒（中位）/ 1.13 秒（最差）** |
| 空闲 20 秒的模型请求数 | — | **0 次**（只有启动那 1 次） |
| 窗口被重绘（像素变了、文字没变） | 会重新问模型 | **0 次** |
| 空闲时每轮开销 | 约 173 ms | **约 18 ms**（跳过 OCR） |
| 单次请求最坏等待 | 60 秒 × 3 次重试 | **25 秒，不重试刷屏，30 秒强制放弃** |

再叠上模型本身约 0.85 秒，**从对方发消息到看见 3 条候选，大约 1.5 秒**。

手机端做了同一套闸门（只在新的对方消息上问、屏幕切换时立刻中断在途请求并释放连接、
25 秒超时、只重试一次、输出预算 320 token、悬浮面板显示已用秒数），
另外把「刷新速度」做成了设置项（极快 0.4 秒 / 快 0.6 秒 / 标准 1 秒 / 省电 2 秒）。

## 十六、怎么用

### 第一步、填一个接口（30 秒）

打开软件 → 右上角「设置」→ 选一个**服务商预设**（DeepSeek / 通义千问 / 智谱 / Kimi /
硅基流动 / OpenAI / OpenRouter / Claude / Gemini / 本地 Ollama……共 20 个），
把 **API Key** 粘进去，点底部的 **「确认保存」**（这个按钮固定在屏幕底部，不会跑）。

想确认配置对不对，点旁边的「保存并测试连接」，状态行会告诉你结果。

### 电脑版：打开就能用，不用框选

1. 打开微信 / QQ / 飞书电脑版的聊天窗口，再打开轻聊助手。
2. 它会**自己认出聊天窗口**（标题栏显示「采集中」），自动切出消息区、
   自动读聊天记录、自动给出「对方最近说」「建议」「紧张度」和 **3 条候选回复**。
   —— 就是视频里那个样子。
3. 面板默认**跟着聊天窗口走**，停在你旁边。
4. 点某条回复下面的 **「填入聊天框」**，它会聚焦聊天窗口、把这句话打进输入框 ——
   **发送键永远由你按**。也可以点「复制」自己粘。

   控制栏上有一行**技能**按钮：`通用` / `军师`，点一下切换、再点一下取消（见第二节）。

   没自动认出来怎么办？在「当前会话」右边的下拉里选一个窗口就行，**选一次就记住了**，
   下次打开直接用。万一某个软件的版式特殊，还可以「手动框选」兜底。

### 手机版：同样不用手动添加

1. 按首页向导开三项权限：**无障碍**、**悬浮窗**、**自启动 + 省电无限制**
   （小米/HyperOS 必做，否则后台被冻结读不到消息）。
2. 打开任意聊天软件进入聊天窗口。
3. 悬浮球出现，对方发新消息时会自动分析并展开，给出意图、紧张度、建议和 3 条候选回复。
4. 点「复制」或「填入」，然后**你自己按发送**。

   面板顶部有一行**技能**按钮：`通用` / `军师`，点一下切换，点第二下取消（见第二节）。

   识别范围：
   - **QQ / X（推特私信）/ 飞书**：专门适配，直接读节点文字，最准。
   - **其它聊天软件**（钉钉、Telegram、WhatsApp、Slack、Discord、Instagram、
     Messenger、LINE、KakaoTalk、企业微信、TIM……）：内置包名识别 +
     「看着像聊天窗口」的形状判断，**自动读，不用手动添加**。
   - **微信手机版**：微信把消息文字对无障碍隐藏了，所以程序用**截屏 + 本地 OCR** 读
     （设置里有「读取微信」开关，默认开）。截屏是微信风控会注意到的行为，
     不想用就把它关掉，关掉后碰到微信只提示一句、不再截屏。

## 十七、自定义第三方 API：怎么做到「支持所有大模型」

所有大模型 API 的差别只在三种线格式里，程序三种都内置：

| 协议 | 请求形状 | 覆盖的服务商 |
|---|---|---|
| **OpenAI 兼容** | `POST {base}/chat/completions`，`Authorization: Bearer <key>` | OpenAI、DeepSeek、通义千问、智谱 GLM、Kimi、硅基流动、火山方舟、腾讯混元、MiniMax、百川、阶跃、零一万物、OpenRouter、Groq、Ollama、LM Studio、One-API/New-API 中转站……绝大多数服务商 |
| **Anthropic** | `POST {base}/messages`，`x-api-key` + `anthropic-version` | Anthropic Claude 官方 API |
| **Google Gemini** | `POST {base}/models/{model}:generateContent?key=<key>` | Google Gemini 官方 API |

预设只是帮你把**地址 + 协议 + 模型**一次填好；选「自定义（任意兼容服务）」
就能填任意地址。地址栏里直接粘一个完整 URL（`…/chat/completions`、`…/messages`、
`…:generateContent`）也会被原样使用，网关路径再怪也能接。

**temperature 留空就不发送这个参数** —— 避开 o1/o3、DeepSeek-R1 这类直接拒绝该参数的推理模型。
**额外请求头**支持一行一条 `Name: value`，用来对接需要特殊 header 的网关。

## 十八、和原项目比，简化了什么

| | 原版 Jev 聊天助手 | 本简化版 |
|---|---|---|
| 接口配置 | 判断 / 回复 / 视觉三路分别配置 | **一个接口**，地址 + 密钥 + 模型 |
| 模型调用 | 两次：判断模型给结论，生成模型写回复 | **一次**：一个提示词同时返回意图、紧张度和 3 条候选 |
| 协议 | OpenRouter / TypeSafe 专用协议 | **OpenAI 兼容 / Anthropic / Gemini 三协议 + 20 个预设** |
| 电脑端读屏 | 需框选聊天区域 | **自动识别窗口 + 自动切消息区**，另提供一键从窗口列表里选 |
| 重复请求 | — | **只在新的对方消息上问**，抖动/重绘/自己发的消息都不触发 |
| 重新生成时 | — | **已显示的候选不清空**，只更新结果，避免手伸过去时卡片消失 |
| 知识库 | 笔记、联系人、历史三套 | **去掉**，只留一句「关系」说明；另外可选挂上开源的**狗头军师技能**（43 篇参考，按对话内容最多带 2 篇） |
| 技能切换 | — | **通用 / 军师 两个按钮，点一下切换、再点一下取消**，两端位置一致 |
| 界面 | 首页 + 设置 + 知识库三页 | 首页 + 设置两页，保存按钮固定在底部 |
| 平台 | 安卓（+ 各自独立的 mac/Windows 仓库） | **安卓 + Windows**（同一套配置与协议逻辑） |
| 保留 | 无障碍采集、悬浮窗、截图 + 本地 OCR、输入框回填 | 全部保留（QQ / X / 飞书适配器、ML Kit 中文离线 OCR、`ACTION_SET_TEXT` 回填 + 剪贴板兜底） |

原版的硬约束一条没丢：不 hook、不注入、不改目标程序、不读其数据库、**绝不自动发送**、
不碰转账红包、密钥不落日志不进 git。

- 打包验收：签名正式 APK（`versionCode 16 / versionName 1.15`）在设备上安装、启动正常，
  只含 `arm64-v8a` 与 `armeabi-v7a`；Windows 安装包装完后注册表
  `DisplayVersion = 1.15`。

**v1.12 重点：连发消息不再卡死（双端）**

- 定位到一个真机制：**丢掉过期答案时没有松开"正在请求"的锁**。慢接口（6 秒）下
  第 2 条消息在请求途中到达 → 之后的生成永远被挡住（电脑端等到看门狗 50 秒，
  手机端没有看门狗，一直卡到下次换会话）。
  `tools/verify_inflight_messages.py` 先复现（`anchor of the follow-up: (none)`），
  修完后同一条测试输出 `【要回的那句】客户那边已经等了两天了` → PASS。
- 手机端另外一处：**窗口句柄变化（表情面板/贴纸弹窗）被当成换了会话**，会把在途答案丢掉，
  然后踩上面那个锁的坑。现在"是不是同一个会话"只看 App + 会话名；
  "来了新消息"仍然让在途答案作废（锚点已经旧了）。两条都有单测。
- 设备实测（模拟器 + 6 秒慢接口，连点两下输入栏发两条）：三次请求依次推进
  （`answered in 6313/6019/6026 ms`），末次请求的锚点就是最新那条消息。
- 另加 `tools/verify_double_message.py`：两条一起到 / 两条短消息隔 0.8 秒到，都 PASS。

**v1.11 重点：换人不再答错人（双端都实测）**

- **电脑端** `tools/verify_conversation_switch.py` 起两个内容完全不同的假会话，四个场景全过：
  ① 切到第二个窗口 → 请求的【要回的那句】变成新窗口的；② 同一个窗口里换联系人 →
  同样跟到新的人；③ 锁定「李四」而屏幕上是「张三」→ **0 次请求**；
  ④ 锁定「李四」后在那窗口里切到「刘工」→ **0 次请求**，切回李四才继续答。
- **手机端**（模拟器 + 微信版式测试 App，`adb logcat`）：
  换联系人 → `conversation changed in the same window (3 chars -> 2 chars)`，
  随即读到新会话内容并发起 **1 次**请求；锁定「李沅汐」后切到「老刘」→
  `pinned to another conversation: skipped (read=老刘)`，**0 次请求**；
  删掉锁定再切 → **1 次**请求。
- 面板新增「对话人」一行（两端一致）：自动跟随 / 锁定某人。

**v1.10 重点：生成速度（双端实测）**

- 找到真正的瓶颈：**推理模型把"思考"当正文生成**，思考多长就等多久。
  同一个军师请求实测 14-25 秒，其中思考 900-1300 token；提示词长短、
  参考文档 1500 字还是 400 字、去掉参考文档，全都改不动它（详见第二节的数据）。
- 解法是加一个"别思考"的参数，双端实测：
  - 电脑端（本机真实微信窗口 + 真实 LongCat）：军师 **3.5 / 5.2 秒**
  - 安卓端（模拟器，`adb logcat` 的 `answered in`）：**2907 / 3082 / 3231 / 6586 ms**
  - 截图：`windows-10-v1.10-installed-fast-agent.png`（装出来的包，读真实微信）、
    `android-24-v1.10-fast-agent.png`（最新那条消息 → 回复直接对上）
- 这个参数不是所有接口都认，所以加了自动回退，并有一个**严格校验请求体的假接口**
  回归测试 `verify_thinking_fallback.py`：第一次靠回退拿到答案、第二次不再白发、
  关掉设置后完全不发 → 三项全过。
